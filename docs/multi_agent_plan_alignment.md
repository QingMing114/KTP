# 多智能体实现与项目申报书的对齐分析（2026-11-03）

> 背景：M1 已实现“子代理即任务、激活即返回、结算进收件箱”的运行时（`ktp/docs/multi_agent_v1_design.md`）。本文对照项目申报书（`_scratch/plan_doc_dump.txt`）中课题 4 与总体技术方案的多智能体要求，判断当前实现的位置与下一步该做什么。
>
> 结论先说：**当前 M1 是申报书“执行管理智能体”的一个子集**。申报书的硬核是**工具级 MoE + 任务依赖图并行调度 + 语义缓存 + 五级容错 + 密态/安全**，这些尚未实现。下一步不应继续在“聊天式委派”上加码，而应转向**任务图并行调度**与**工具级门控**。

## 3. 判断：M1 的位置与偏差

1. **M1 对齐的是申报书“执行管理智能体”的交互形态**（谁来做、何时返回、结果怎么回传），不是课题4 的核心指标。
2. 前段时间优先做**工具化**（单一实现、spec、注册、统一 invoke）恰好是申报书“工具执行模块 + 元数据层”的地基，方向正确；**不应回退**。
3. 继续堆“聊天式委派/多角色对话”对申报书验收帮助有限；真正能形成课题4 成果的是**任务图并行调度 + 语义缓存 + 容错 + 资源/安全**。
4. 有一个结构性缺口：申报书要求工具容器化与标准化 API 层，而当前工具是**同进程 Python 函数**。短期不必上 Docker（工程成本高），但需要把 `registry.invoke` 当作“进程内 API 层”，并在文档中明确“容器化是部署形态，不是语义边界”，保留未来替换空间。

## 4. 修订路线（按申报书验收优先级）

| 阶段 | 内容 | 对应申报书 | 验收 |
|---|---|---|---|
| **M2 任务图与并行调度** | 新增 `v2/scheduling/task_graph.py`（节点/依赖/关键路径/就绪队列）与 `executor_pool.py`（有界线程池 + 资源标签 CPU/GPU/IO）；工作流步骤由线性执行改为图执行 | 712–726 | 独立子任务并行：同一工作流 wall-clock 下降 ≥30%（LAI/作物/报告的依赖允许时）；调度轨迹可回放 |
| **M3 工具级 MoE 门控** | 基于 `ToolSpecV2` + 语义检索（先复用 RAG embedding，无则用关键词）产出候选工具；门控规则（能力匹配、可用性、成本、历史成功率）选择并记录理由 | 649–663 | 同一子任务在多工具间选择可解释；gating 决策进 trace |
| **M4 语义缓存 + 五级容错** | 缓存：任务/数据/参数三段 key + 相似度阈值 + 差异补偿；容错：retry→migrate→substitute→degrade→skip，逐级可测 | 727–755 | 注入故障（超时/输入不合格/工具异常）后任务仍完成并标注降级；重复任务命中缓存 |
| **M5 安全可信与评测** | 权限/审计/密态**接口**（不实现加密算法，先做 seam 与访问日志）；千级并发压测 harness 与指标看板 | 282–292 | 压测报告：并发数、P50/P95 时延、失败率；审计可追溯 |

M1 子代理运行时保留，作为 M2 图节点的“执行者”之一（不再是唯一形态）。

## 5. 明确不做（近期）

- 群体智能演化/元学习/多智能体 RL：需要仿真环境与训练数据，列入远期，不在本迭代。
- 真实加密算法与密钥体系：需要安全方案评审，先做接口与审计。
- 容器化改造：部署形态问题，不阻塞算法与调度研究。

## 6. 需要决策的点

1. M2 先做**调度**（推荐，直接支撑“多任务协同”指标）还是先做**门控/缓存**（更快见效）？
2. 千级并发指标如何采信：单机压测即可，还是需要gpu208 上的压测报告作为课题材料？
3. 密态是否要在本课题周期内给出可运行的最小实现，还是先接口+审计日志？
